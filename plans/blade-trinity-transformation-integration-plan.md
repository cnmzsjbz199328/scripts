# BladeTrinity 三流派变身素材整合执行计划

日期：2026-11-02。供其他 agent 执行；本轮只制定计划，不修改游戏。

## 0. 已确认用途与资源形式（2026-11-02 修订）

用户确认：三套变身用于现有蓄力技能，用服饰与形象逐步变化表达蓄力。资源沿用既有人物管线：源视频抽帧 → 抠绿 → 透明精灵图集 → Phaser 按蓄力状态选帧。MP4 仅为制作源素材，游戏运行时不加载视频播放器。触发方式已确定为现有蓄力输入。

工作区证据：README.md 第 94 行明确专用蓄力动画缺失，目前借 guard；game/systems/charge.js 第 41 行同样注明“无专用蓄力帧，借 guard 姿势占位”。现有入口为按住 L / 手柄 ZR，AI 也经 _startCharge。仓库证据确认蓄力素材缺口；“变身过程表达蓄力”的具体选择以本次用户确认作为设计依据，不把代码占位注释夸大为完整历史聊天记录。

执行要求：

1. 素材 agent 按真实画面拆分 charge_enter（开始变装）、charge_progress（变装推进）、charge_hold（变装完成后的稳定姿势）与 release（挥剑）区间，记录源帧号。完整六秒只供预览，不能强迫玩家蓄满六秒。
2. _startCharge 替换 guard 占位；_tickCharge 以 clamp((time-chargeFrom)/BT.CHARGE.fullMs,0,1) 驱动变装进度，不以视频自播放墙钟驱动。满蓄后保持稳定终态，不循环整段变身或提前挥剑。只用变装段，严禁把视频末端攻击混入持续蓄力。
3. 保持现有 fullMs、minFrac、扣蓝、起浪、玩家松键、AI 自动松手、受击中断与失焦/掉线取消规则。不得新增血量门槛、每局次数限制、额外伤害或无敌。
4. 提前松手按现有阈值决定取消或释放；取消时清理展示并恢复普通表现。有效释放时，优先保留现有 attack 和剑气逻辑，设计短暂可读的服饰回落衔接。若采用源片 release 段，必须另行标定对应刀线与出剑气帧，不能继续套旧 BLADE_MARKS/QI_SEGS 导致剑气错位或重复发射。
5. 变装只表达本次蓄力，不要求永久新服饰动作集。不得在 charge 状态内提前恢复普通服饰；释放/取消后的恢复必须在实际预览中验收。
6. 增加验收：短按、半蓄、满蓄、满蓄继续按住、耗蓝归零、受击、失焦、手柄掉线、AI 蓄力、双方同时蓄力。进度与蓄力比例一致，满蓄不再变大、不转头、不自动攻击，取消不发剑气，正常释放剑气数量与伤害保持原规则。

## 4. 阶段 A：独立素材处理

执行 agent：素材 agent。使用 video-sprite 既有管线，在独立的 video_runs/BladeTrinityTransform/{sword,water,north}/ 工作区处理，避免直接修改既有七动作 manifest、图集或共享处理器。

1. 检查实际绿幕颜色、黑边、全动作运动范围和薄剑刃。新片不能套用旧源片 crop=712:716:284:2 的裁切参数。
2. 先用原生帧率检查全段，标记原装保持、服饰变化、展示剑招、最终保持四段的实际边界。
3. 以单帧 192×208、脚底基线 202 为初始兼容规格；保持宽高比，使用跨全段固定裁剪窗与固定缩放。严禁逐帧 trim/逐帧自动适配造成角色呼吸式放大。若使用 anchor，必须检查它没有消除原动作或引入位置抖动。
4. 每个角色与自身现有 idle 对比身体高度和脚底位置；用人物身体作尺度参考，不能把整把剑的 bbox 高度当成人物高度。允许角色间体型差异。
5. 全段原生抽帧用于审查与分段；运行时只取有效变装序列和满蓄保持帧。初始目标变装段 16–21 帧，按实际动作清晰度调整，不能把重复保持帧和后段挥剑均匀混采进蓄力序列。源片时间戳只用于制作追溯，不决定游戏蓄力时长。独立网格图集每边不得超过 4096；需要时用多行网格或分图。
6. 抠绿并检查白发、白衣、银边、双剑、手脚和半透明水效；黑/白/暖色背景分别目检。不增加全屏闪光遮盖瑕疵。
7. 输出透明图集、元数据、完整接触表、首末帧对比、尺寸/基线记录、可复现命令与审查报告。

验收门 A：剑与手脚不裁切；无大片绿边；北神保持源片头部方向；中段无新增尺度变化；服饰变化清楚。失败时只调整本项目参数，不能为此全局改写共享抠图逻辑。

## 5. 阶段 B：播放组件与资源注册

执行 agent：前端 agent。A 的元数据契约确定后可接入；A 完成前可搭预览外壳。

建议运行时资源：assets/sprites/transform/{sword,water,north}.webp；元数据使用 assets/sprites/transformations.js 注册 window.BT.TRANSFORM_ATLAS，包含纹理路径、单格尺寸、网格列数、chargeFrames、holdFrame、基线、初始朝向、源帧号映射。可选 releaseFrames 独立存储。蓄力帧序列由进度选帧，不注册为自动循环动画；fps 只用于审查预览。路径以最终产物为准。

沿用 script 加载约定，不能依赖 fetch 被忽略的 JSON。现有 atlases.js 和七行动作保留原契约。需要检查新增成品确实进入版本控制及部署资源，而不只是本机存在。

新增 game/systems/transformation.js（或符合项目现有组织的等价模块），提供 begin、setProgress、end 和资源失败回退。setProgress 用 clamp(p,0,1) 映射 chargeFrames 索引，p=1 固定 holdFrame；不能每 tick 重启动画。展示层依附真实 fighter 的位置、朝向、深度及可见性，复用现有描边策略。若用独立 sprite，隐藏原 sprite 的显示，避免双人重影；不要改变真实碰撞体、速度、HP 或命中计算。

确保左右双方都正确镜像，播放期间不因自动朝向更新而突然翻面。动画结束、加载失败、重开、换角色、场景销毁、角色死亡时都能清理，完成回调最多执行一次。资源失败时立即恢复现有角色表现，不阻塞对局。

验收门 B：项目内预览可按角色、左右朝向、不同背景拖动 0–100% 蓄力进度，并模拟按住、满蓄保持、释放和取消；无 404、无自动循环、无累计残影或重复监听器。

## 6. 阶段 C：游戏触发和服饰衔接

沿现有 charge 生命周期接入玩家 L / 手柄 ZR 和 AI 蓄力。当前 BT.CHARGE.fullMs 为 420ms；以实际配置计算进度，不把 420 写死在表现模块。满蓄后继续按住保持 holdFrame；松手、蓝量耗尽、受击、失焦/断线分别沿原逻辑释放或取消。

服饰衔接是必验项：蓄力期间保留当前进度的变装表现，满蓄保持新服饰；释放或取消后按第 0 节恢复对应既有动作，并目检过渡。此次无需永久新服饰动作集。源片后段挥剑不自动接入攻击判定；若使用，必须完成独立刀线标定和剑气时序验证。

验收门 C：玩家与 AI 真实蓄力路径均可达；变装帧与蓄力比例一致；满蓄稳定保持；取消及时清理；释放仍按原规则生成剑气；原有动作和规则无回归。必须完成真实对局接入，不能仅以独立预览作为交付完成。

## 8. agent 分工与交接顺序

1. 素材 agent 执行 A，独占新素材工作区及 transform 资源目录，提交图集契约与报告。
2. 前端 agent 负责 B、C，独占游戏 JS 和加载入口；先阅读素材契约再接最终资源。不得同时改素材脚本参数。
3. 验收 agent 在前两项完成后检查第 7 节，记录问题到具体角色/时刻/朝向，交原负责人修复并复验。

单 agent 执行时按 A→B→C→验收顺序。多 agent 执行时也不共享修改同一注册表或脚本。此计划本身不要求部署或发布。
